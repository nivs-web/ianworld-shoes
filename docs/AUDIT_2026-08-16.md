`src/` 전체(게임 로직 · services · 멀티 · 화면 · 성능/PWA)를 영역별로 나눠 훑고,
발견한 것은 전부 **파일·줄 단위로 코드를 다시 열어 확인**했다.
"이러면 더 좋다" 류 취향 제안은 전부 뺐고, **재현 경로가 있는 것만** 남겼다.

심각도 순. 각 항목의 `확인` 은 내가 코드로 직접 확정했다는 뜻이고,
`검증 필요` 는 콘솔/실기기에서 1~2분이면 확정할 수 있는데 아직 안 해 본 것이다.

## 1. RTDB 규칙의 상위 `.write` 가 하위 방어선을 전부 무력화한다 · 치명 (확인)

`docs/FIREBASE_RULES.md:99`

```json
"$code": {
  ".write": "auth != null && (... data.child('players').child(auth.uid).exists() ...)",
  "players": { "$uid": { ".write": "auth.uid == $uid" } },      // ← 평가되지 않음
  "result": { "given": { "$uid": { ".write": "auth.uid == $uid" } } }  // ← 평가되지 않음
}
```

RTDB는 **상위에서 허용하면 하위 `.write` 를 아예 보지 않는다**(shallower rules override deeper).
`$code` 에 쓰기를 열어 뒀으므로 방에 들어간 사람은 **방 전체를 마음대로 쓸 수 있고**,
"남의 계단 수는 못 고친다 / `given` 은 본인만 쓴다"는 두 방어선이 실제로는 없다.

악용 절차 (콘솔 한 줄):
1. 비밀방을 만든다 → `players/{나}` 가 생기므로 `$code` 쓰기 권한 획득
2. `set(ref(db,'rooms/<code>'), { players:{나:…, 가짜uid:{stairs:0,shoesFound:0,alive:false}},
   result:{ rankings:[나,가짜uid], given:{ 가짜uid:[0,0,0,…수백개] } } })`
3. 결과 화면을 열거나 다음 접속의 `sweepUnsettled` 를 태운다
4. `multiSettle.js:98-103` 이 검증 없이 `addShoes()` + `recordShoe()` → **지갑 수천 켤레, 도감 130/130 즉시 완성**,
   `pushWallet()` 이 Firestore 로 밀어 올려 신발왕 1위

실제 대전에서도 상대의 `players/{상대uid}/stairs` 를 0으로 덮거나 `rankings` 를 미리 박을 수 있다.

**고칠 방향**: `$code` 최상위 `.write` 를 없애고 쓰기 가능한 자식(`state`·`open`·`startAt`·
`difficulty`·`result/rankings`)만 각각 연다. `players` 와 `result/given` 은 상위를 `false` 로 끊고
자식에서만 허용. `given` 에 길이·값 범위 `.validate` 추가(예: 최대 4개, 0~129 정수).

## 2. `hostUid` 검증식이 입장·퇴장·결과확정을 통째로 거부할 수 있다 · 치명 (검증 필요)

`docs/FIREBASE_RULES.md:101`

```json
"hostUid": { ".validate": "!data.exists() || data.val() == auth.uid" }
```

조건이 `newData` 가 아니라 **기존 값이 나여야 통과**다. 그런데 `joinRoom`(`multiplayer.js:130`),
`leaveRoom`(`:310`), `finalizeResult`(`:284`)는 전부 `runTransaction` 으로 **방 노드 전체**를 다시 쓴다.
쓰기 데이터에 `hostUid` 가 늘 포함되므로, 값이 안 바뀌어도 방장이 아닌 사람은 여기서 걸린다.

예상 증상: **방은 만들어지는데 아무도 못 들어온다.** 화면에는 원인 대신 "네트워크 오류" 토스트만
뜬다(`joinRoom` 이 catch 후 `'error'` 반환). 방장이 아닌 사람의 이탈·순위 확정도 같이 막힌다.

멀티는 아직 실기기 2인 대전을 한 번도 안 돌렸으므로 **첫 실전에서 바로 터질 후보 1순위**다.
Firebase 콘솔 → Realtime Database → 규칙 → 시뮬레이터로 1분이면 확정된다.

**고칠 방향**: `newData.val() == data.val() || !data.exists() || data.val() == auth.uid`

## 3. 로그아웃이 로컬 저장을 안 지운다 → 계정 전환 시 남의 재산이 이식된다 · 치명 (확인)

`src/services/auth.js:163-168` · 로그아웃 버튼은 `src/screens/Portal.js:25` 에 실재한다

```js
export async function signOut() {
  if (fb) await fb.authMod.signOut(fb.auth);
  current = null;  // ← localStorage 는 그대로
  emit();

```

`storageLocal.js:476` 에 `resetAll()` 이 이미 있는데 **호출부가 0건**이다.

재현: A 계정으로 신발 80켤레·도감 60종을 모은다 → 포털에서 로그아웃 → B 계정으로 로그인.

4. 명예의 전당에 같은 이름·같은 기록이 두 계정으로 올라간다

**고칠 방향**: `signOut()` 에서 `L.resetAll()`. 그리고 로그인 시 저장된 uid 와 새 uid 가 다르면
로컬을 비우고 시작(로그아웃 없이 계정만 바뀌는 경로 대비).

## 4. 판이 끝나도 캔버스 씬이 살아 있다 · 높음, 전 사용자 (확인)

`src/screens/startGame.js:65` · `src/screens/startMultiGame.js:39`

`Scene.reset()` 은 게임을 **시작할 때만** 불린다(`startGame.js:40`, `startMultiGame.js:26`).

세 가지 증상이 전부 여기서 나온다:

- **(a) 멀티 결과 화면에서 사망 효과음이 난다.** 상대가 먼저 죽어 내가 살아 있는 채로 결과 화면에
  가면, 씬 스택 맨 위가 여전히 `GameScene` 이라 `update()` 가 계속 돈다 → 게이지가 계속 닳고
  0이 되는 순간(보통 난이도 약 3.7초 뒤) `sfx_death` → 24프레임 뒤 `sfx_fall` 이 결과 화면에서 울린다.
- **(b) 로비·도감·명예의전당을 보는 내내 인게임을 60fps로 그린다.** `body.ui-mode #stage{display:none}`
  라 눈에만 안 보일 뿐, 배경 3레이어 + 계단 17칸 + 캐릭터 + HUD 드로우 콜은 그대로 나간다.
  **M8 완료 기준의 "발열 점검"에 정면으로 걸린다.**
- **(c) `exit()` 이 안 불려** `setTapHandler`/`setPauseHandler` 와 `Stairs`·`Player` 참조가 남는다.

**고칠 방향**: `handleFinish` 와 멀티 `onFinish` 에서 `Scene.reset()`(빈 씬) 또는
`while (Scene.depth()) Scene.pop()`. 겸사겸사 `renderAll()` 이 `ui-mode` 일 때 통째로 건너뛰게 한다.

## 5. 정산 도장이 로컬에만 있고 200건에서 잘린다 → 신발이 저절로 복제·증발한다 · 치명 (확인)

`src/services/multiSettle.js:70,105` · `src/services/storageLocal.js:392-397`

정산 중복 방지 도장(`sf_settledMatches`)은 **localStorage 에만** 있는데, 재정산의 입력인
`userRooms/{uid}` 와 `result.given` 은 **RTDB에 영구히 남는다**(방을 지우는 코드가 없다).
게다가 `markSettled` 는 200건이 넘으면 **오래된 도장부터 지운다**.

두 경로 모두 치팅 없이 발생한다:

- **기기를 바꾸거나 저장소를 지우면**: `everPlayedMulti()` 가 원격 `multiWins` 로 참이 되고
  `sweepUnsettled` 가 옛 방을 다시 훑는다 → 승자는 같은 `given` 을 **또 걷고**(`mergeWallet` 이
  신발별 `max` 병합이라 그대로 굳는다), 패자는 신발을 **또 낸다**.
- **150판쯤 하면**: 한 판에 도장이 1~4개 찍히므로 상한에 닿아 옛 도장이 잘려 나간다 →
  같은 일이 저절로 일어난다. 오래 즐긴 사람일수록 확실히 겪는다.

부수적으로 `sweepUnsettled` 가 매 접속마다 **지금까지의 모든 방**을 순회한다(무료 요금제 읽기 직격).

**고칠 방향**: 도장을 `rooms/{code}/result/settled/{uid}` 에 남긴다(서버가 진실).
정산이 끝난 방은 `userRooms` 에서 지운다. sweep 은 최근 N개만 훑는다.

## 6. 멀티에서 일시정지 → 나가기로 "이기고 도망"이 된다 · 높음 (확인)

`src/game/GameScene.js:373 leave()` · `src/screens/startMultiGame.js:32-40` · `multiplayer.js:286`

멀티에도 일시정지가 그대로 살아 있고(`bindInput` 에 멀티 분기 없음), 일시정지 메뉴의
`로비로나가기`·`게임재개` 둘 다 `leave()` → 멀티 `onFinish` 로 간다. 그런데 멀티 `onFinish` 는
인자를 무시하고 **무조건 `finalizeResult(code)`** 를 부른다. 이건 이미 순위가 있으면 덮지 않는
트랜잭션이라 **처음 부른 사람이 그 시점 진행도로 순위를 영구 확정**한다.

악용: 신발 1켤레를 먼저 줍는다(1순위 정렬 키) → 화면 상단을 탭해 일시정지
(이때 내 게이지는 멈추고 상대는 계속 뛴다) → `로비로나가기` → 순위 `[나, 상대]` 확정.
상대는 200계단을 올라도 패자로 정산돼 신발을 상납한다.

부수 피해: `leave()` 는 `exitMulti()` 도 `reportDeath()` 도 안 부른다. 내 `alive` 가 `true` 로
남아 **남은 사람은 자기가 죽을 때까지 방이 안 끝나고**, 살아 있는 `roomUnsub` 때문에 로비나
도감을 보다가 갑자기 멀티 결과 화면으로 튕길 수 있다.

**고칠 방향**: 멀티에서는 일시정지를 막거나 "포기하고 나가기"로 명시한다.
나갈 때 `reportDeath()` 를 먼저 보내고 `exitMulti()` 로 구독을 끊는다.

## 7. `collection.js` 만 `withTimeout` 을 안 써서 로그인 화면에 영구히 갇힌다 · 높음 (확인)

`src/services/collection.js:67` (`getDocs`) · `:56` (`batch.commit`)

CLAUDE.md §9-0-7이 기록한 함정 — **파이어스토어 쓰기는 reject 되지 않고 영원히 pending 한다** —
때문에 `profile.js` 와 `leaderboard.js` 는 모든 호출을 `withTimeout` 으로 감쌌다.
그런데 `collection.js` 는 `withTimeout` 을 **import조차 하지 않는다.**

재현: 파이어스토어가 막히는 환경(사내망·일부 통신사·확장 프로그램)에서 로그인 →

`finally { busy = false }` 에 도달하지 못해 **버튼이 완전히 죽는다.** 새로고침 말고 방법이 없다.

**고칠 방향**: `collection.js` 의 원격 호출을 전부 `withTimeout` 으로 감싼다.
`_lint-services.mjs` 에 "services 안의 `getDocs`/`getDoc`/`setDoc`/`commit` 은 반드시
`withTimeout` 과 같은 줄/블록에 있어야 한다" 규칙을 넣어 재발을 막는다.

`onLeave() { reqId++; }` 한 줄이면 막힌다.

## 10. HUD 외곽선이 렌더 비용을 정확히 9배로 만든다 · 중, 발열/60fps (확인)

`src/core/pixelfont.js:68-74` — `outline` 이면 8방향 `blit()` + 본체 = **글리프를 9번 찍는다**.
HUD의 세 텍스트(계단수·신발수·부활수)가 전부 `outline` 을 쓴다(`hud.js:51,58,66`).

폰트 비트마스크로 실제 `fillRect` 런 수를 계산한 값:

| 항목 | 런 | ×9 |
|---|---|---|
| 계단수 3자리(scale 2) | 37 | 333 |
| 신발수 2자리 | 24 | 216 |
| 부활 1자리 | 13 | 117 |
| 계단 17칸 그림자·외곽선 + 구름 | — | 58 |
| **합계** | | **~724 fillRect / frame = 초당 43,440회** |

180×320 캔버스에 초당 4만 번 넘는 `fillRect` 다. 중저가 안드로이드에서 60fps를 깨는 1순위 후보이고,
4번(로비에서도 계속 그림)과 겹치면 **메뉴에 가만히 있어도** 이 비용이 나간다.

**고칠 방향**: HUD 텍스트를 오프스크린 버퍼에 굽고 **값이 바뀔 때만** 다시 굽는다.
계단수는 한 칸 오를 때만, 신발수·부활수는 획득 시에만 바뀌므로 사실상 0에 수렴한다.

## 이상 없음을 확인한 것 (다시 안 봐도 되는 곳)

- **상태 초기화**: 재시작·부활·씬 재진입에서 남는 값 없음. 매 판 새 `GameScene` 인스턴스이고
  모듈 전역(`bgm` trackIdx, `multiplayer` 스로틀)도 각각 리셋 경로가 있다.
- **정수 좌표(§3-2)**: 렌더 전 경로에서 소수 좌표가 도달하지 않는다. `sprite.js` 가 `Math.floor` 로 최종 방어.
- **고정 타임스텝**: 100ms 클램프 + 탭 복귀 시 `acc=0`. 순간이동·스파이럴 없음.
- **경계값**: 층수 0/1, 100·200·300·400·500 전환, 게이지 0, 신발 인덱스 0, 부활 0개, 엘리베이터 500층 — 정상.
- **기간 키**: ISO 주차(목요일 기준) 계산 정상. 조회와 제출이 같은 함수를 쓴다.
- **연타 중복 실행**: 로그인·방 만들기·코드 제출·닉네임·구매 전부 가드가 있다.
- **`refresh` vs `mount` 규약**: 도감 티어탭·캐릭터 index·순위표 탭 전부 인스턴스 변수로 보존된다.
- **큐 상한**: `queueScore` 50건, `markSettled` 200건 — 무한히 자라는 경로 없음(단 5번·12번 참고).
- **`ctx.fillText` 사용처 0건**, 매 프레임 `getBoundingClientRect` 없음, 초기 번들 분리 정상.
- **localStorage 예외**: 전부 try/catch 라 게임이 멈추지 않는다(다만 `write()` 의 실패 반환값을
  아무도 안 보므로 저장 실패가 무증상으로 지나간다).
